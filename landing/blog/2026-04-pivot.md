# Why we pivoted from FreeMail to AgentComms

*Published on `agentcomms.dev/blog/pivot` — 2026-04-18*

If you knew this project as FreeMail, this is the story of why it became AgentComms and what changed in the public API.

## The thesis we started with

Ten months ago we started FreeMail on a narrow thesis: AI agents need email addresses, traditional providers don't sell one programmatically, so we'd build the infrastructure. Tiny wedge. Fast to launch. Differentiated enough against Gmail/Outlook that early adopters showed up and built real workflows.

The wedge worked. For a minute.

## What changed in the market

Over eight weeks the agent-email category commoditized. The lesson was direct: a mailbox alone is not durable infrastructure for agents. Email remains important, but it is only one channel in a wider communications surface.

Narrow wedges win when the incumbent is slow and the category is new. When the category matures in weeks, narrow wedges lose to broader platforms that bundle more of the agent's actual job.

## The broader thesis we missed at first

Agents don't need email. Agents need to communicate. The set of channels they need is huge and growing — email, SMS, Slack, Telegram, Discord, WhatsApp, mobile push, physical letters, fax, voice. The platforms that win in agent infra are the ones that cover the whole surface, normalize it into a sensible abstraction, and let the agent's reasoning layer ignore which channel a message came in on.

So we pivoted. FreeMail became AgentComms. The product moved from "email for agents" to **one unified inbox across every channel**, deployed into your own AWS account, and open source under Apache-2.0.

## The differentiator

The practical bet is coding-agent-friendly self-hosting: your coding agent can install and deploy AgentComms into your own AWS account from a written contract.

```bash
npm i -g @agentcomms/cli
agentcomms bootstrap --domain your-domain.com --admin-email you@your-domain.com --json
```

That's the whole thing. A coding agent with AWS credentials and a domain runs one command. The resulting hub runs in that AWS account - DynamoDB, Lambda, API Gateway, SES, SNS, SQS, Kinesis, KMS, and Bedrock wired up - under the user's control, serving unified messages across email, SMS, Slack, Telegram, push, and external adapter channels.

The NDJSON output stream is structured so coding agents can parse progress. Exit codes are structured so they know what to do on failure. The docs are written for a coding agent to follow, not a human.

## The architectural bets

**Agent-centric data model.** Inboxes are gone. The top-level object is the `Agent`. Each agent has N channels underneath it (email, SMS, Slack bot, Telegram bot, push target). The unified inbox is one DynamoDB query — every direct message and mention from every channel, interleaved by time, with channel-native detail preserved in an opaque blob for the agent's reasoning layer to decode.

**Plugin adapter SDK.** Each channel is a module under `adapters/` implementing a `ChannelAdapter` contract. Adding a new channel means copying an existing adapter, changing ~300 lines, landing a PR. Community bounties for the first Discord and WhatsApp implementations are open.

**AWS-native end to end.** Nothing else. No Kafka, no Redis, no Postgres. DynamoDB single-table, Lambda, SES, Bedrock, SNS, SQS, Kinesis, API Gateway. The whole thing deploys via CDK. Your coding agent doesn't have to understand or operate a stack it doesn't already know.

## The license

Apache-2.0. You can self-host, modify, run internally, redistribute modified versions, build commercial products, and operate hosted services on top of it. There is no field-of-use restriction, delayed relicensing period, or separate paid license required by this repository.

We landed here after considering permissive, copyleft, restricted-source, and delayed-open models. The answer for this project is real OSS. Agent communications infrastructure should be easy to inspect, fork, embed, and extend; the durable moat should be product quality, operational competence, trust, and adapter coverage.

## What changed for existing users

The current API surface is agent-centric. New integrations should use `Agent`, `Channel`, `UnifiedMessage`, and agent-scoped routes under `/v1/agents/*`. Legacy FreeMail/VictoryMail migration notes remain in the repository for operators who need cutover context, but the public quickstart, SDKs, MCP server, and adapter guides all target AgentComms.

If you are migrating old code, replace old inbox/pod assumptions with agent/channel modeling, update SDK imports to `agentcomms` or `@agentcomms/client`, and use `api.agentcomms.dev` or your self-hosted bootstrap URL as the base URL.

## What's actually live today

- Five channels (email, SMS, Slack, Telegram, push) operational in production.
- Agent-centric REST API + Python SDK + Node SDK + MCP server with 24 tools.
- One-command CDK deploy via the `agentcomms` CLI.
- Full Apache-2.0 licensing and CI coverage across Python, Node SDK, MCP, CLI, CDK, examples, and the adapter template.
- Source at `github.com/IntergalacticTech/agentcomms`.
- Hosted at `agentcomms.dev`.

## What's next

Discord and WhatsApp adapters (bounties open). Postal mail via Lob and fax via Phaxio. Semantic search over the unified inbox via OpenSearch Serverless. Multi-region failover. SOC 2 for enterprise deployments.

None of those unlock value that the current five channels don't already. They make the hub more complete for agents that need them. If you need one of those and we haven't shipped it yet, open an issue; we prioritize based on what agents in the wild are asking for.

## How to try it

If you want a managed hosted deployment: sign up at `agentcomms.dev`.

If you want the source and a deployment in your own AWS account: `git clone` the repo, read `AGENT.md`, run `agentcomms bootstrap`.

If you want to pick up a bounty or contribute an adapter: check the GitHub issues labeled `bounty` and `good-first-adapter`. The Telegram adapter is the cleanest template.
