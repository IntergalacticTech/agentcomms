# Email Threading Implementation

## Overview

Email threading groups related messages into conversations. This is essential for AI agents that need to understand the context of a conversation -- an agent replying to a customer support inquiry needs to see the full thread, not isolated messages. AgentMail implements threading based on RFC 5256 (a simplified version of the JWZ threading algorithm) using three standard email headers and a subject-based fallback.

## RFC 5256 Threading Algorithm

RFC 5256 defines two threading algorithms: ORDEREDSUBJECT and REFERENCES. AgentMail implements a simplified version of the REFERENCES algorithm (originally designed by Jamie Zawinski for Netscape, commonly called "JWZ threading").

### Simplified JWZ Algorithm (as implemented in AgentMail)

The full JWZ algorithm builds an in-memory tree of all messages, resolves parent-child relationships, prunes phantom nodes, and groups by subject. This is designed for IMAP servers that need to present a thread view of an entire mailbox.

AgentMail simplifies this because:

1. We assign messages to threads on arrival (one at a time), not in batch
2. We store thread_id on each message in DynamoDB -- we don't rebuild the tree on every query
3. We use DynamoDB atomic operations for thread state instead of in-memory tree manipulation

Our algorithm reduces to: **for each incoming message, find the existing thread it belongs to (or create a new one).**

## Headers Used

Three RFC 5322 headers drive threading:

### Message-ID

```
Message-ID: <unique-id@domain.com>
```

- Generated by the sending mail client or server
- Globally unique identifier for a specific message
- Format: `<local-part@domain>` (angle brackets required)
- AgentMail generates: `<msg_xxxxxxxxxxxx@agentmail.dev>`
- Stored in DynamoDB and indexed via GSI5 for reverse lookup

### In-Reply-To

```
In-Reply-To: <parent-message-id@domain.com>
```

- Contains the Message-ID of the message being replied to
- Set by the replying client (standard behavior for Reply/Reply All)
- Single value (though RFC allows multiple, this is rare)
- This is the strongest threading signal

### References

```
References: <root-message-id@domain.com> <mid1@domain.com> <mid2@domain.com> <parent-message-id@domain.com>
```

- Contains the full chain of Message-IDs from the thread root to the immediate parent
- Built by appending the parent's Message-ID to the parent's References list
- First entry is the thread root
- Last entry is the immediate parent (same as In-Reply-To)
- This provides thread lineage even when intermediate messages are missing

### How Clients Set These Headers

| Action | Message-ID | In-Reply-To | References |
|---|---|---|---|
| New message | Generated | Empty | Empty |
| Reply to message A | Generated | A's Message-ID | A's References + A's Message-ID |
| Reply to reply B (which replied to A) | Generated | B's Message-ID | A's Message-ID + B's Message-ID |
| Forward message A | Generated | Usually empty | Usually A's Message-ID |

### Example Thread

```
Message 1 (original):
  Message-ID: <msg001@acme.agentmail.dev>
  In-Reply-To: (none)
  References: (none)
  Subject: Order #12345 inquiry

Message 2 (reply to 1):
  Message-ID: <reply001@customer.com>
  In-Reply-To: <msg001@acme.agentmail.dev>
  References: <msg001@acme.agentmail.dev>
  Subject: Re: Order #12345 inquiry

Message 3 (reply to 2):
  Message-ID: <msg002@acme.agentmail.dev>
  In-Reply-To: <reply001@customer.com>
  References: <msg001@acme.agentmail.dev> <reply001@customer.com>
  Subject: Re: Order #12345 inquiry

Message 4 (reply to 1, branching):
  Message-ID: <reply002@customer.com>
  In-Reply-To: <msg001@acme.agentmail.dev>
  References: <msg001@acme.agentmail.dev>
  Subject: Re: Order #12345 inquiry
```

Messages 1-4 all belong to the same thread. Message 4 creates a branch (two replies to message 1), but AgentMail treats the thread as a flat list ordered by timestamp, not a tree.

## Thread Resolution Algorithm

### Overview

```
Incoming message
      │
      ▼
┌─────────────────────────────────────────────────┐
│ Strategy 1: In-Reply-To Lookup                   │
│ Look up In-Reply-To header value in GSI5         │
│ (PK=MSGID#{rfc_message_id})                      │
│                                                   │
│ Found? → Use that message's thread_id             │
│ Not found? → Continue to Strategy 2               │
└────────────────────────┬────────────────────────-┘
                         │
                         ▼
┌─────────────────────────────────────────────────┐
│ Strategy 2: References Chain Lookup               │
│ Iterate through References header (all entries)   │
│ Look up each in GSI5                              │
│                                                   │
│ Found any? → Use that message's thread_id         │
│ None found? → Continue to Strategy 3              │
└────────────────────────┬─────────────────────────┘
                         │
                         ▼
┌─────────────────────────────────────────────────┐
│ Strategy 3: Subject Normalization Fallback        │
│ Strip Re:/Fwd:/Fw:/Aw:/Sv:/Vs:/Ref: prefixes     │
│ Normalize whitespace and case                     │
│ Search recent threads in this inbox for match     │
│ (within 30-day window)                            │
│                                                   │
│ Found? → Use that thread_id                       │
│ Not found? → Continue to Strategy 4               │
└────────────────────────┬─────────────────────────┘
                         │
                         ▼
┌─────────────────────────────────────────────────┐
│ Strategy 4: New Thread Creation                   │
│ Generate new thread_id: thr_{uuid}               │
│ Create thread record in DynamoDB                  │
│ This message becomes the thread root              │
└─────────────────────────────────────────────────┘
```

### Detailed Pseudocode

```python
def resolve_thread(
    table,
    inbox_id: str,
    in_reply_to: str,       # e.g., "<msg001@acme.agentmail.dev>"
    references: list[str],  # e.g., ["<msg001@acme.agentmail.dev>", "<reply001@customer.com>"]
    subject: str,           # e.g., "Re: Order #12345 inquiry"
) -> str:
    """
    Resolve which thread an incoming message belongs to.

    Returns a thread_id (either existing or newly generated).

    This function is the heart of AgentMail's threading system.
    It must be fast (called on every inbound message) and correct
    (wrong thread assignment breaks conversation context for AI agents).
    """

    # ═══════════════════════════════════════════════════════════════
    # STRATEGY 1: In-Reply-To Lookup
    #
    # The In-Reply-To header contains the Message-ID of the message
    # being replied to. This is the strongest and most reliable
    # threading signal.
    #
    # We look up this Message-ID in GSI5:
    #   GSI5 PK: MSGID#{rfc_message_id}
    #   GSI5 SK: MSG#{msg_id}
    #
    # If we find a match, we use that message's thread_id.
    # ═══════════════════════════════════════════════════════════════

    if in_reply_to:
        # Clean the Message-ID (some clients add whitespace or extra brackets)
        clean_irt = _clean_message_id(in_reply_to)

        if clean_irt:
            response = table.query(
                IndexName='GSI5',
                KeyConditionExpression=Key('GSI5_PK').eq(f'MSGID#{clean_irt}'),
                Limit=1,
                ProjectionExpression='thread_id, inbox_id, message_id'
            )

            if response['Items']:
                parent = response['Items'][0]
                thread_id = parent['thread_id']

                # Validate: thread is not at max capacity
                if _thread_has_capacity(table, inbox_id, thread_id):
                    return thread_id
                else:
                    # Thread is full -- create a continuation thread
                    return _create_continuation_thread(
                        table, inbox_id, thread_id, subject
                    )

    # ═══════════════════════════════════════════════════════════════
    # STRATEGY 2: References Chain Lookup
    #
    # The References header contains the full chain of Message-IDs
    # from the thread root to the immediate parent. We check each
    # one (starting from the first, which is the thread root).
    #
    # The first Reference that matches gives us the thread.
    # Starting from the root is important: it finds the thread
    # even if some intermediate messages were sent to a different
    # inbox or were lost.
    # ═══════════════════════════════════════════════════════════════

    if references:
        for ref in references:
            clean_ref = _clean_message_id(ref)
            if not clean_ref:
                continue

            response = table.query(
                IndexName='GSI5',
                KeyConditionExpression=Key('GSI5_PK').eq(f'MSGID#{clean_ref}'),
                Limit=1,
                ProjectionExpression='thread_id, inbox_id'
            )

            if response['Items']:
                thread_id = response['Items'][0]['thread_id']
                if _thread_has_capacity(table, inbox_id, thread_id):
                    return thread_id

    # ═══════════════════════════════════════════════════════════════
    # STRATEGY 3: Subject Normalization Fallback
    #
    # When In-Reply-To and References are both missing or don't
    # match any known message, we fall back to subject matching.
    #
    # This handles:
    # - Clients that strip threading headers (rare but exists)
    # - Forwarded messages where someone starts a new reply chain
    # - Messages from legacy systems without proper threading
    #
    # We normalize the subject by:
    # 1. Stripping reply/forward prefixes (Re:, Fwd:, Fw:, etc.)
    # 2. Collapsing whitespace
    # 3. Lowercasing
    # 4. Comparing against recent threads in the same inbox
    #
    # Constraints:
    # - Only match threads within the same inbox
    # - Only match threads within a 30-day recency window
    # - Only match if the normalized subject is non-trivial (>3 chars)
    # ═══════════════════════════════════════════════════════════════

    normalized_subject = _normalize_subject(subject)

    if normalized_subject and len(normalized_subject) > 3:
        # Query recent threads for this inbox
        response = table.query(
            KeyConditionExpression=(
                Key('PK').eq(f'INB#{inbox_id}') &
                Key('SK').begins_with('THR#')
            ),
            ScanIndexForward=False,  # Most recent first
            Limit=50,  # Check last 50 threads
            ProjectionExpression='thread_id, subject, last_message_at, message_count'
        )

        now_ms = int(time.time() * 1000)
        thirty_days_ms = 30 * 24 * 60 * 60 * 1000

        for thread in response.get('Items', []):
            # Skip threads older than 30 days
            thread_age = now_ms - thread.get('last_message_at', 0)
            if thread_age > thirty_days_ms:
                break  # Sorted by recency, so no more recent threads after this

            # Compare normalized subjects
            thread_normalized = _normalize_subject(thread.get('subject', ''))
            if thread_normalized == normalized_subject:
                thread_id = thread['thread_id']
                if _thread_has_capacity(table, inbox_id, thread_id):
                    return thread_id

    # ═══════════════════════════════════════════════════════════════
    # STRATEGY 4: New Thread Creation
    #
    # No existing thread matched. Create a new one.
    # ═══════════════════════════════════════════════════════════════

    new_thread_id = f'thr_{uuid.uuid4().hex[:20]}'
    return new_thread_id


# ═══════════════════════════════════════════════════════════════════════
# HELPER FUNCTIONS
# ═══════════════════════════════════════════════════════════════════════

def _clean_message_id(raw: str) -> str:
    """
    Clean a Message-ID header value.

    Handles various malformations:
    - Extra whitespace: " <id@domain> " → "<id@domain>"
    - Missing brackets: "id@domain" → "<id@domain>"
    - Double brackets: "<<id@domain>>" → "<id@domain>"
    - Multiple IDs (take first): "<id1@a> <id2@b>" → "<id1@a>"
    """
    if not raw:
        return ''

    raw = raw.strip()

    # If multiple IDs (space-separated), take the first
    if ' ' in raw and '<' in raw:
        parts = re.findall(r'<[^>]+>', raw)
        if parts:
            raw = parts[0]

    # Remove extra brackets
    while raw.startswith('<<') and raw.endswith('>>'):
        raw = raw[1:-1]

    # Add brackets if missing
    if raw and not raw.startswith('<'):
        raw = f'<{raw}>'
    if raw and not raw.endswith('>'):
        raw = f'{raw}>'

    # Validate basic structure
    if re.match(r'^<.+@.+>$', raw):
        return raw

    return ''


def _normalize_subject(subject: str) -> str:
    """
    Normalize a subject line for thread matching.

    Strips all reply/forward prefixes according to RFC 5256 and
    common client variations. Case-insensitive. Collapses whitespace.

    Examples:
      "Re: Order #12345"          → "order #12345"
      "RE: RE: RE: Hello"         → "hello"
      "Fwd: Re: Meeting notes"    → "meeting notes"
      "Fw: [URGENT] Alert"        → "[urgent] alert"
      "AW: Bestellung #789"       → "bestellung #789"  (German "Antwort")
      "SV: Møte i morgen"         → "møte i morgen"    (Norwegian "Svar")
      "Re[2]: Status update"      → "status update"
    """
    if not subject:
        return ''

    # Iteratively strip prefixes (handles "Re: Fwd: Re: ...")
    # Pattern matches: Re:, RE:, Fwd:, FW:, Fw:, Aw:, Sv:, Vs:, Ref:
    # Optionally with [N] suffix: Re[2]:, Re[4]:
    # Leading whitespace at each level
    previous = None
    normalized = subject
    while normalized != previous:
        previous = normalized
        normalized = re.sub(
            r'^\s*(Re|Fwd|Fw|Aw|Sv|Vs|Ref)\s*(\[\d+\])?\s*:\s*',
            '',
            normalized,
            flags=re.IGNORECASE
        )

    # Collapse whitespace
    normalized = re.sub(r'\s+', ' ', normalized).strip()

    # Lowercase for comparison
    return normalized.lower()


def _thread_has_capacity(table, inbox_id: str, thread_id: str) -> bool:
    """Check if a thread is below the maximum message count."""
    response = table.get_item(
        Key={
            'PK': f'INB#{inbox_id}',
            'SK': f'THR#{thread_id}'
        },
        ProjectionExpression='message_count'
    )
    if 'Item' in response:
        return response['Item'].get('message_count', 0) < THREAD_MAX_MESSAGES
    return True  # Thread doesn't exist yet -- will be created


def _create_continuation_thread(
    table, inbox_id: str, parent_thread_id: str, subject: str
) -> str:
    """
    Create a continuation thread when the parent thread is at max capacity.

    The continuation thread references the parent for navigation.
    """
    new_thread_id = f'thr_{uuid.uuid4().hex[:20]}'
    now_ms = int(time.time() * 1000)

    table.put_item(Item={
        'PK': f'INB#{inbox_id}',
        'SK': f'THR#{new_thread_id}',
        'thread_id': new_thread_id,
        'inbox_id': inbox_id,
        'subject': subject,
        'message_count': 0,
        'participants': set(),
        'continuation_of': parent_thread_id,  # Link to parent thread
        'created_at': now_ms,
        'last_message_at': now_ms,
    })

    # Update parent thread to point to continuation
    table.update_item(
        Key={
            'PK': f'INB#{inbox_id}',
            'SK': f'THR#{parent_thread_id}'
        },
        UpdateExpression='SET continued_by = :new_thread',
        ExpressionAttributeValues={':new_thread': new_thread_id}
    )

    return new_thread_id
```

### Atomic Counter Updates

When a new message is added to a thread, we update the thread record using DynamoDB atomic operations. This ensures correctness even when multiple messages arrive concurrently for the same thread.

```python
def update_thread_on_new_message(
    table,
    inbox_id: str,
    thread_id: str,
    message_id: str,
    subject: str,
    sender_address: str,
    all_participants: list[str],  # from + to + cc
    timestamp_ms: int,
    is_new_thread: bool = False
):
    """
    Update thread state when a new message is added.

    Uses atomic DynamoDB operations:
    - ADD for incrementing message_count (atomic counter)
    - ADD for appending to participants set (set union)
    - ADD for appending to message_ids set (set union)
    - SET for updating last_message_at (idempotent overwrite)
    """

    if is_new_thread:
        # Create new thread record
        table.put_item(
            Item={
                'PK': f'INB#{inbox_id}',
                'SK': f'THR#{thread_id}',
                'thread_id': thread_id,
                'inbox_id': inbox_id,
                'subject': subject,
                'message_count': 1,
                'participants': set(all_participants),
                'message_ids': {message_id},
                'last_message_at': timestamp_ms,
                'created_at': timestamp_ms,
                'status': 'active',
                'GSI4_PK': f'THR#{thread_id}',
                'GSI4_SK': f'MSG#{timestamp_ms}#{message_id}',
            },
            ConditionExpression='attribute_not_exists(PK)',  # Prevent overwrite race
        )
    else:
        # Atomic update to existing thread
        table.update_item(
            Key={
                'PK': f'INB#{inbox_id}',
                'SK': f'THR#{thread_id}'
            },
            UpdateExpression=(
                # SET: overwrite scalar fields
                'SET last_message_at = :ts, '
                '    updated_at = :ts, '
                '    #status = if_not_exists(#status, :active), '
                '    GSI4_PK = :gsi4pk, '
                '    GSI4_SK = :gsi4sk '
                # ADD: atomic increment and set union
                'ADD message_count :one, '
                '    participants :participants, '
                '    message_ids :msg_set'
            ),
            ExpressionAttributeNames={
                '#status': 'status'
            },
            ExpressionAttributeValues={
                ':ts': timestamp_ms,
                ':active': 'active',
                ':one': 1,
                ':participants': set(all_participants),
                ':msg_set': {message_id},
                ':gsi4pk': f'THR#{thread_id}',
                ':gsi4sk': f'MSG#{timestamp_ms}#{message_id}',
            }
        )
```

### Thread Query Patterns

```python
# ── List threads in an inbox (sorted by most recent activity) ────────
def list_threads(table, inbox_id: str, limit: int = 20, cursor: str = None):
    """List threads for an inbox, most recent first."""
    params = {
        'KeyConditionExpression': (
            Key('PK').eq(f'INB#{inbox_id}') &
            Key('SK').begins_with('THR#')
        ),
        'ScanIndexForward': False,  # Descending (most recent first)
        'Limit': limit,
    }
    if cursor:
        params['ExclusiveStartKey'] = json.loads(cursor)

    response = table.query(**params)
    return response['Items'], response.get('LastEvaluatedKey')


# ── List messages in a thread (sorted by timestamp) ─────────────────
def list_thread_messages(table, thread_id: str, limit: int = 50, cursor: str = None):
    """List messages in a thread using GSI4, oldest first."""
    params = {
        'IndexName': 'GSI4',
        'KeyConditionExpression': Key('GSI4_PK').eq(f'THR#{thread_id}'),
        'ScanIndexForward': True,  # Ascending (oldest first = conversation order)
        'Limit': limit,
    }
    if cursor:
        params['ExclusiveStartKey'] = json.loads(cursor)

    response = table.query(**params)
    return response['Items'], response.get('LastEvaluatedKey')


# ── Get thread with latest messages (combined query) ─────────────────
def get_thread_with_messages(table, inbox_id: str, thread_id: str, message_limit: int = 20):
    """Get thread metadata and its most recent messages."""

    # Parallel queries
    thread_response = table.get_item(
        Key={
            'PK': f'INB#{inbox_id}',
            'SK': f'THR#{thread_id}'
        }
    )

    messages_response = table.query(
        IndexName='GSI4',
        KeyConditionExpression=Key('GSI4_PK').eq(f'THR#{thread_id}'),
        ScanIndexForward=True,
        Limit=message_limit,
    )

    return {
        'thread': thread_response.get('Item'),
        'messages': messages_response['Items']
    }
```

```python
# ── Delete thread and all messages ──────────────────────────────────
def delete_thread(table, inbox_id: str, thread_id: str):
    """
    Delete a thread and all its messages.

    This is a destructive operation. Messages are permanently removed.
    """
    # Get all messages in the thread
    messages = table.query(
        IndexName='GSI4',
        KeyConditionExpression=Key('GSI4_PK').eq(f'THR#{thread_id}'),
        ProjectionExpression='PK, SK'
    )

    # Batch delete messages
    with table.batch_writer() as batch:
        for msg in messages['Items']:
            batch.delete_item(Key={'PK': msg['PK'], 'SK': msg['SK']})

        # Delete the thread record itself
        batch.delete_item(Key={'PK': f'INB#{inbox_id}', 'SK': f'THR#{thread_id}'})
```

## Edge Cases

### Missing Headers

**Problem:** Some email clients or legacy systems don't set `In-Reply-To` or `References` headers, even for replies.

**Detection:** The message has `Re:` in the subject but no `In-Reply-To` or `References`.

**Solution:** Fall through to Strategy 3 (subject normalization). The `Re:` prefix gets stripped, and we match against existing thread subjects in the inbox.

```python
# Example: message with subject "Re: Invoice #456" but no threading headers
# → normalized to "invoice #456"
# → matched against existing thread with subject "Invoice #456"
```

**Risk:** False positive thread matching. Two unrelated threads with the subject "Hello" would be incorrectly merged. We mitigate this with the 30-day recency window and by requiring a minimum subject length (>3 characters after normalization).

### Cross-Inbox Threads

**Problem:** A conversation might involve multiple AgentMail inboxes. For example:
- `support@acme.com` (inbox A) receives a customer email
- `support@acme.com` forwards to `billing@acme.com` (inbox B)
- `billing@acme.com` replies -- the reply's `In-Reply-To` points to a message in inbox A

**Decision:** Each inbox maintains its own independent threads.

**Rationale:**
1. Threads are scoped to inboxes for access control (different API keys may access different inboxes)
2. AI agents typically operate on a single inbox
3. Cross-inbox threading creates complex data access patterns that complicate the DynamoDB schema

**Implementation:** When the GSI5 lookup finds a parent message in a different inbox, we treat it as if no match was found and fall through to subject matching or new thread creation.

```python
# In the resolve_thread function, after Strategy 1 GSI5 lookup:
if response['Items']:
    parent = response['Items'][0]
    parent_inbox = parent.get('inbox_id')

    # Only use this thread if the parent is in the same inbox
    if parent_inbox == inbox_id:
        return parent['thread_id']
    else:
        # Cross-inbox reference -- log but don't thread
        logger.info(
            f'Cross-inbox reference: message In-Reply-To points to '
            f'inbox {parent_inbox}, but recipient inbox is {inbox_id}'
        )
        # Fall through to next strategy
```

**Future option:** A `related_threads` field could link cross-inbox threads for advanced use cases.

### Forwarded Messages

**Problem:** Forwarded messages create ambiguity:
- The `Fwd:` prefix in the subject suggests it's part of an existing conversation
- But forwarding creates a new conversational context
- Some clients set `References` to include the original message chain; others don't

**Solution:**

```python
def _is_forward(subject: str, in_reply_to: str, references: list) -> bool:
    """Detect if a message is a forward rather than a reply."""
    # Strong signals of forwarding:
    # 1. Subject starts with Fwd: or Fw: (but not Re:)
    # 2. No In-Reply-To header (forwards typically don't set this)
    # 3. References is empty or matches the forwarded message only

    subject_lower = subject.lower().strip()
    starts_with_fwd = any(
        subject_lower.startswith(prefix)
        for prefix in ['fwd:', 'fw:', 'forwarded:']
    )

    has_reply_to = bool(in_reply_to)

    return starts_with_fwd and not has_reply_to
```

For detected forwards, we create a new thread rather than attaching to the original:

```python
if _is_forward(subject, in_reply_to, references):
    # Start a new thread -- this is a new conversational context
    new_thread_id = f'thr_{uuid.uuid4().hex[:20]}'
    return new_thread_id
```

### Mailing List Messages

**Problem:** Messages from mailing lists often have modified headers:
- `Reply-To` is set to the list address
- `References` may include the list's message IDs
- Subject is prefixed with `[list-name]`

**Solution:** Strip mailing list subject prefixes during normalization:

```python
def _normalize_subject(subject: str) -> str:
    # ... existing normalization ...

    # Also strip mailing list tags: [foo], [bar-baz]
    normalized = re.sub(r'\[[\w-]+\]\s*', '', normalized)

    return normalized.lower().strip()
```

### Race Conditions

**Problem:** Two messages for the same thread arrive simultaneously. Both attempt to create the thread record.

**Solution:** The `put_item` for new threads uses a condition expression:

```python
table.put_item(
    Item=thread_item,
    ConditionExpression='attribute_not_exists(PK)'
)
```

If the second write hits the condition, it falls back to `update_item` (which is idempotent):

```python
try:
    table.put_item(Item=thread_item, ConditionExpression='attribute_not_exists(PK)')
except dynamodb.meta.client.exceptions.ConditionalCheckFailedException:
    # Thread was created by a concurrent message -- update instead
    update_thread_on_new_message(table, inbox_id, thread_id, ...)
```

### Message-ID Collisions

**Problem:** Two different messages arrive with the same `Message-ID` header (shouldn't happen per RFC, but some systems reuse IDs).

**Solution:** GSI5 maps `Message-ID` to the first message stored. Subsequent messages with the same `Message-ID` are stored but their GSI5 entry points to the first occurrence. This is acceptable because Message-ID collisions in practice are between duplicates of the same message, not different messages.

### Very Long Reference Chains

**Problem:** A thread with hundreds of messages builds a very long `References` header. Some mail servers truncate it.

**Solution:** We only need to find one matching reference. Checking the first entry (thread root) and the last entry (immediate parent) covers 99% of cases. If the middle of the chain is truncated, we still match.

```python
if references:
    # Optimization: check first and last references first
    # (root and parent), then scan the rest if needed
    priority_refs = []
    if references:
        priority_refs.append(references[0])     # Thread root
    if len(references) > 1:
        priority_refs.append(references[-1])     # Immediate parent
    # Add remaining references
    priority_refs.extend(references[1:-1])

    for ref in priority_refs:
        match = _lookup_message_by_rfc_id(table, ref)
        if match:
            return match['thread_id']
```

## Thread Limits

### AgentMail Thread Limits

| Limit | Value | Rationale |
|---|---|---|
| Max messages per thread | 100 | DynamoDB item size constraints, API response size, practical UX |
| Max threads per inbox | Unlimited | Threads are DynamoDB items, no practical limit |
| Max participants per thread | 500 | DynamoDB set size limit (400KB item) |
| Thread subject max length | 998 characters | RFC 5322 header line limit |
| Thread recency window (subject match) | 30 days | Prevent false matches on old conversations |
| Min subject length for matching | 4 characters | Prevent matching on trivially short subjects |

### Thread Continuation

When a thread reaches 100 messages, new messages create a continuation thread:

```
Original Thread (thr_001):
  message_count: 100
  continued_by: thr_002

Continuation Thread (thr_002):
  continuation_of: thr_001
  message_count: 23
```

The API can be queried to traverse the chain:

```
GET /v1/threads/thr_001
→ { "id": "thr_001", "message_count": 100, "continued_by": "thr_002" }

GET /v1/threads/thr_001/messages?include_continuations=true
→ Returns messages from thr_001 + thr_002
```

### Why 100 Messages?

1. **DynamoDB query performance.** Querying 100 messages via GSI4 returns in <50ms. At 1,000 messages, pagination becomes necessary and latency increases.
2. **API response size.** 100 messages with body previews (4KB each) = ~400KB response. Larger responses slow down AI agent processing.
3. **AI context windows.** AI agents processing a thread need to fit it in their context window. 100 messages with previews is roughly 50K-100K tokens, which fits in most modern context windows.
4. **Practical conversations.** Most email threads have 3-15 messages. The 100 limit is generous and only hit by high-volume automated threads.
